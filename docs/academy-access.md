# Academy course access

The dedicated `/academy/courses/[slug]` pages reuse published course records and existing account sessions. Landing-page data, public content DTOs, and local demo data are unchanged. Demo previews are not commerce records and cannot be enrolled in or redeemed against.

## Configuration and administration

Existing SUPER_ADMIN and ACADEMY_MANAGER sessions can open `/admin/academy-access`. Other roles cannot manage access or scholarships. Existing `admin:access` and `courses:edit` permission checks and CSRF defenses apply.

Run the existing `npm --prefix backend run db:indexes` command against the intended database before enabling access. It now includes the Academy collections, including orders and verified payment events. Transactions require MongoDB configured as a replica set; a standalone server fails closed. No data migration or production configuration is performed automatically.

Load a published course slug, then save its versioned access configuration. Fields include `enabled`, integer-paisa `regularPriceMinor`, optional lower `salePriceMinor`, currency `BDT`, optional `saleStartsAt`/`saleEndsAt` ISO timestamps, actual `accessTerms`, supplied `benefits`/`outcomes`, optional `category`, `description`, `audience`, `instructor`, approved public `previewVideoUrl`, optional `thumbnail`, and `modules`. A thumbnail has `src` and meaningful `alt` fields; src must be one of the verified existing assets `/banner/iot_banner.jpg`, `/banner/esp32Bannetr.jpg`, `/banner/aibanner3.jpg`, `/banner/academy_2.jpg` or `/banner/b2.jpg`. Arbitrary remote/private URLs are rejected. A module has an ID, title and supplied lessons. A lesson has a stable unique ID, title, description, `text` or `video` type, and one access mode:

- `public`: visitors can open the first introductory video and associated resources. Later video lessons cannot be public.
- Legacy `account` flags no longer bypass enrollment. Only an explicitly public first introduction is accessible without enrollment; every later lesson, including text and resources, requires active enrollment.
- `enrolled`: an active server enrollment is required.

Text lessons require supplied plain text. Supplied video lessons use a private `.mp4` or `.webm` file key. A missing file key is allowed so incomplete lessons remain visible with Video not supplied, and no player is offered. File availability is verified under the private media root before advertising playback. An approved course preview URL can supply only the first public video. Optional `durationSeconds` must reflect known source data. Resources have IDs, titles and private file keys. Syllabus topics in old course records remain topics; they are not converted into invented lessons.

Scholarship management supports eligible published course slugs, percentage/fixed/full discounts, start and expiry, total/per-account limits, optional verified recipient email, active/revoked state and versioned edits. Recipient-restricted codes require the account email to be verified before use. The raw code is provided only on input and stored as a hash, never returned. Store it securely; edits require the same raw code. Course eligibility or revocation changes affect new redemptions; previously granted enrollments are separately revocable. Admin grant/revoke requires an existing enabled account ID.

## Access and pricing

Authentication uses existing HttpOnly sessions, fresh enabled-user/role checks and CSRF checks. Academy-specific login/signup entry routes preserve a validated course return destination and use the existing account endpoints; there is no separate account system.

Free enrollment, admin grants and full scholarships are server records. Account creation alone does not grant paid-course access. Percentage and fixed discounts are calculated from the approved regular price in minor units. Sale and code discounts never stack: the better single discount applies. Fixed-code amounts use `amountMinor`; legacy whole-BDT `amount` values remain readable without changing existing documents. Discount amounts are capped at the subtotal, and final totals cannot be negative. A zero final amount can be redeemed as a scholarship. Code application alone creates no enrollment and consumes no redemption. Full redemption atomically writes its redemption, enrollment, counter and audit record. Concurrent attempts are serialized by transaction conflicts; retries return the existing active enrollment without consuming another use. Revoked enrollments cannot self-reactivate through a new code/free retry.

There is no configured payment provider. Nonzero balances cannot be paid. Server order summaries are supported with a blocked status; they never grant access or reserve code capacity. No successful payment, progress, review, bundle or certificate is simulated. A payment-derived enrollment can be created only by the verified internal settlement path described below.

## Media boundary

Set `ACADEMY_MEDIA_ROOT` to an absolute path on a **private** backend volume outside any public web/static directories. Provision approved production lesson files there; this implementation does not upload media or invent file URLs. Only simple approved-extension file keys are accepted. Real-path checks reject symlinks escaping the configured root.

Public Academy metadata contains only lesson titles, type, supplied duration, resource count and access rules. It contains no restricted text, private file keys or protected media URLs. Lesson-content and every media/resource request recheck the published/enabled course, authenticated session and enrollment. Protected files stream through those endpoints with no-store headers and range support. Downloaded resources use attachment disposition. Public YouTube embeds are allowed only as approved course previews, not as protected paid lessons. Preview dialogs unmount playback on close.

A private source volume, supplied production media, configured access terms/prices and the indexes are required for live use. DRM, CDN signing and payment integrations are not configured in this pass.

## Authenticated orders and promo reservations

`AcademyService` remains the single authority for pricing, code eligibility and enrollment. `GET /academy/courses/:slug/commerce` exposes public readiness and approved pricing; authenticated `GET /academy/courses/:slug/order-summary` adds course-specific enrollment. Complete explicitly enabled courses show Buy course, returning guests through existing login/signup to `/academy/courses/:slug/order`. Other courses offer a non-purchasable summary. `POST /academy/courses/:slug/orders` accepts only an idempotency key and optional raw code, recalculates integer-paisa totals and stores a server order. Client prices, currency, discounts and payment statuses are rejected. An identical authenticated key returns its existing order; a changed course/code with that key is rejected. Owned orders are available at `GET /academy/orders` and `GET /academy/orders/:id`; the cart route lists them and reopens their summaries.

Admin purchase availability uses the existing courses:edit roles and revision/audit system. Complete actual stored lesson descriptions/content, available media/resources and configured pricing are required to enable purchases. Generated syllabus placeholders and the 24 illustrative catalog previews cannot be sold. Existing course pricing is preserved. Free enrollment and full-discount scholarship access reuse existing server enrollment transactions; no payment step is introduced for zero totals.

Existing `best-single-discount` policy is preserved: one code per order, choose the better of the configured sale and a code discount against the regular price, never stack them. Codes now include integer-paisa minimumSpendMinor, tested against the current sale price. Active/dates/course/account/verified-recipient checks remain server-side with explicit safe error messages. Totals cannot be negative. Applying a code only quotes it.

With a configured provider, pending orders reserve code capacity for up to 15 minutes, bounded by code expiry. Redemption and reservation counts are checked in the same Mongo transaction; updating the code revision serializes concurrent reservations, admin edits and redemptions. Pending holds count toward both total and per-account limits. Verified payment consumes the hold and records the redemption/enrollment atomically. Failed/cancelled orders release it; expired timestamps immediately stop counting toward capacity, and reading an expired order marks/releases/audits it transactionally. No scheduler is required for expired capacity to become available. Full scholarships consume capacity and create enrollment in one transaction, with unique order/redemption/enrollment indexes preventing retry duplication.

## Backend-generated distribution codes

Authorized SUPER_ADMIN/ACADEMY_MANAGER users can open `/admin/academy-access` → Generate scholarship codes. Enter an admin label, eligible published course slugs and a future local expiry; choose 1–100 codes. The default is a 100% scholarship with totalLimit=1 and perAccountLimit=1. Reusable generation requires enabling the explicit-limit control and specifying total/per-account limits. Copy all codes or individual codes before hiding them or leaving the page. Codes are held only in component memory, never browser storage. The scholarship list refreshes after generation; existing edit/revoke controls remain available.

`POST /api/v1/admin/academy/scholarships/generate` uses the existing admin:access/courses:edit guard, session/CSRF checks, Scholarship schema, hash normalization/validation and audits. It accepts count (default 1, maximum 100), label, courses, future expiresAt and optional startsAt, totalLimit, perAccountLimit, recipientEmail, minimumSpendMinor, kind/amount/amountMinor. Omitted kind is full and omitted limits are 1. Partial kinds reuse existing percentage/fixed validation. No client-supplied raw code, price, active flag or revision is accepted. Eligible slugs must be published courses; illustrative catalog previews cannot be redeemed against.

Each code is generated on the backend with Node crypto.randomBytes(24), yielding 192 bits of entropy. It is stored using the existing SHA-256 code hash and unique index. A batch and one scholarship_generate audit per code commit atomically; the audit records the actor and code-record ID, never the raw code. Revocation records the actor through the existing scholarship_revoke audit. Raw codes appear only in the successful authorized generation response (`Cache-Control: private, no-store`), not in subsequent admin lists, public course data, audits or logs. Generation results cannot be recovered from hashes; an uncertain generation response requires checking and revoking unwanted records before regenerating.

Students use the unchanged Apply → Confirm order flow. Apply never enrolls. Confirmation revalidates and atomically consumes a full scholarship, creates its order and grants enrollment. Existing idempotency, concurrency limits, role/CSRF protections and lesson/media ownership checks are reused. Positive balances remain subject to real verified payment; no payment is simulated. `GET /api/v1/academy/my-learning` now lists only the authenticated account’s active enrollments in published courses, and the existing My Learning route renders those records with Continue learning. The list includes no restricted lesson media, fabricated progress or student counts.
